## 三、发现的问题

### 问题 1（严重）：监听服务被系统解绑后**不会自动重连**

**现象**：用户在微信里转账付款，App 一条记录都没有，界面也没有任何提示。

**排查过程**：

```bash
# ① 授权状态：显示已开启
adb shell settings get secure enabled_notification_listeners
# → ...:com.moneyflow.app/com.moneyflow.app.capture.NotificationCaptureService   ← 有

# ② 实际绑定状态：没有
adb shell dumpsys notification | sed -n '/Live notification listeners/,/Snoozed/p'
# → 11 个 live listener 里没有 com.moneyflow.app                                   ← 没有

# ③ 进程是活的，包也没被停用
adb shell ps -A | grep moneyflow          # → pid 存在
adb shell dumpsys package com.moneyflow.app | grep stopped
# → User 0: ... stopped=false ...                                                ← 正常

# ④ 打开 App 想靠 onResume 自愈 —— 无效，绑定数仍是 0

# ⑤ 把系统开关关掉再打开 —— 立刻恢复
adb shell cmd notification disallow_listener com.moneyflow.app/com.moneyflow.app.capture.NotificationCaptureService
adb shell cmd notification allow_listener    com.moneyflow.app/com.moneyflow.app.capture.NotificationCaptureService
adb shell logcat -s NotificationCapture
# → I/NotificationCapture: 通知监听已连接                                          ← 恢复
```

**结论**：

「通知使用权已开启」（静态授权）和「监听服务被系统绑上」（动态状态）**是两件事**。
HyperOS 上出现过前者为真、后者为假，且：

- 打开 App 不能恢复（原代码里 `onResume` 的 `requestRebind` 在真机上**无效**，已实测）
- 只有「把系统开关关掉再打开」有效

**影响**：用户付了钱，App 一条通知都收不到，且毫无提示 —— 这是最糟的失败模式。

**已做的修复**：

1. 新增看门狗：`KeepAliveService` 每 60 秒检查一次「已授权但未连接」，
   发现就主动请求重绑（尽力而为，不保证 ROM 一定响应）
2. 设置页的提示文案原来写「退出重进本页面即可恢复」—— **实测是错的**，已改成
   唯一有效的操作步骤，并新增「已授权·未连接」这个中间状态显示
3. 补充小米「自启动」的必做提示

**修复后的真机验证（已通过）**：

复现掉线状态（覆盖安装后打开 App，监听确实没绑回来），然后观察看门狗：

```
W/KeepAliveService: 已授权但监听未连接，第 1 次请求重连       ← 21:43:15
W/KeepAliveService: 已授权但监听未连接，第 2 次请求重连       ← 21:44:15，确认是按周期重试
   ↓ 执行设置页写的「把开关关掉再打开」
I/NotificationCapture: 通知监听已连接                        ← 21:45:26
I/KeepAliveService: 通知监听已恢复（之前掉线 3 次）           ← 21:46:15，检测到恢复后停止重试
```

**结论（重要且必须如实说明）**：

- 看门狗**能检测**掉线并持续尝试重连 —— 这部分工作正常
- 但 **HyperOS 会忽略 App 发起的重连请求**，看门狗重试 3 次都没能绑回来
- 真正救回来的是**手动把系统开关关掉再打开**

所以在小米这类 ROM 上，看门狗只是「多试几次」，**不能替代手动步骤**。
设置页因此把手动步骤放在最显眼的位置，这是有意为之，不是没做自动化。

### 问题 2（严重，产品层面）：**收不到「应用分身」的通知**

**现象**：抓到的微信通知里，有一半来自 `user 999`。

```bash
adb shell pm list users
# → UserInfo{0:机主} running
# → UserInfo{999:XSpace} running          ← 小米应用分身空间

adb shell pm list packages --user 999 | grep -c com.tencent.mm     # → 1（分身里有微信）
adb shell pm list packages --user 999 | grep -c com.moneyflow.app  # → 0（我们没装在那）
adb shell dumpsys notification | grep 'user 999'
# → (user 999): All notification listeners (0) enabled for current profiles
```

**结论**：

Android 的通知监听**按用户空间隔离**。装在主空间的 App，**原理上不可能**收到分身空间里
微信/支付宝的通知。这不是能靠改代码绕过的，是系统设计。

**影响**：用「应用分身」的微信/支付宝付款，等于完全没被记录，而且用户看不出来。

**已做的修复**：

1. 设置页明确写出这个限制和对策（改用主空间支付，或用「导入账单」补记）
2. README 如实写明

### 问题 3（轻微）：验证码短信被误留档

**现象**：

```
pkg=com.android.mms   text='微信支付 【微信支付】027626(微信支付验证码,请勿泄露),'
```

这条被当成「疑似账务样本」存进了 `raw_samples`。但它既没有账务价值，
又包含敏感的临时凭证 —— 而 README 明确承诺过「验证码不会被记录」。

**根因**：判断「看起来和钱有关」的关键词表里有「微信支付」，这条短信命中；
而判定逻辑**根本没有排除验证码**。更糟的是这个判定在两个文件里**各写了一份**
（`NotificationCaptureService` 和 `SmsReceiver`），改一处漏一处。

**已做的修复**：

1. 抽出唯一的实现 `parse/MoneyText.kt`，两个通道都用它
2. 加入验证码排除（验证码/校验码/动态码/动态密码/短信密码/verification code）
3. 新增 `MoneyTextTest`，把这条真机样本固定成回归测试

### 问题 4（严重）：微信**付款**被记成**收入**（方向记反）

**发现方式**：2026-10-14 第二次测试，用 JVM 直接跑解析引擎（不依赖 adb 伪造通知）。

**现象**：

```
输入：微信支付 收款方：星巴克 ¥38.50        ← 这是一笔「付款」
旧行为：记账 38.5 INCOME（收入）             ← 记反了
正确：EXPENSE（支出）
```

**根因**：

`wechat_receive` 的正则里用了裸的「收款」二字：

```kotlin
Regex("""(?:收款|到账|收到).*?[¥￥]?\s*([\d,]+\.?\d*)""")   // 旧
```

微信**付款**通知里写着「**收款方**：星巴克 ¥38.50」——
「收款方」是名词（指商家），整句语义是**支出**，但裸「收款」命中了它。
而这条规则优先级是 **20**，`wechat_pay_merchant` 只有 **15**，
所以付款规则根本没机会跑 —— 支出被记成收入，**统计彻底反向**。

支付宝的 `alipay_receive` 有一模一样的问题（也有「收款方」字样）。

**顺带发现的同类问题**：`.*?` 会跨字段抓数字，把无关数字当成金额：

| 文本 | 旧规则抓到 | 应该是 |
|---|---|---|
| 微信支付 零钱提现 **手续费 0.10** 元 到账 500.00 元 | 0.10 ❌ | 500.00 |
| 微信支付 提现 **订单号 12345678** 金额 500.00 | 12345678 ❌ | 500.00 |
| 云闪付 交易提醒 **卡号 6225** 消费 58.00 元 | 6225 ❌ | 58.00 |

**已做的修复**：

1. income 规则只保留**能确定是资金入账**的写法：
   `收款到账 / 收款成功 / 已收款 / 收款通知 / 收到转账 / 收到一笔 / 收到红包 / 到账`，
   并要求金额紧跟在动词之后（不再用 `.*?` 跨字段）
2. 微信/支付宝两条 income 规则都改
3. 新增 `wechat_withdraw_settled`（优先级 23）处理「手续费…到账 N」形态，
   保证取到的是**到账金额**而不是手续费
4. `rule_check.py` 里内嵌的规则副本同步更新，并**新增 6 条样本**守住这个 bug

**验证**（都实际跑过）：

| 验证项 | 结果 |
|---|---|
| 新回归测试在**旧规则**下 | ✅ 如期 **FAIL**（证明测试真能抓住这个 bug） |
| 新回归测试在**修复后** | ✅ PASS |
| JVM 用例总数 | ✅ **133 个全通过**（原 128 + 新增 5） |
| `tools/rule_check.py` | ✅ 35/35 通过 |
| 银行短信覆盖率 | ✅ 19/19（无回归） |
| 结构自检 / 括号检查 | ✅ 通过 |
| 引擎实测 6 条关键用例 | ✅ 6/6 通过 |

**新增回归测试**（`ParseEngineJUnitTest`）：

- `wechatPayeeLabelIsNotMistakenForIncome` —— 「收款方」必须判为支出
- `wechatPayeeLabelVariantsStayExpense` —— 各种「收款方/收款账户」变体
- `alipayPayeeLabelIsNotMistakenForIncome` —— 支付宝同样的坑
- `realIncomePhrasingsStillWork` —— 修复不能把真正的收入也堵死
- `withdrawDoesNotCaptureFeeOrOrderNumber` —— 不能把手续费当提现金额

> 教训：**「收款」和「收款方」只差一个字，方向却完全相反。**
> 规则里凡是**名词性**的词（收款方、付款方、收款账户）都不能当作方向依据，
> 只有**动词性**的（已收款、收款到账）才可以。

## 四、已证实的正确行为

### 全链路在真机上跑通

用 `adb shell cmd notification post` 伪造一条支付通知（**注意**：`adb shell` 会把命令
再解析一次，文本必须整体加引号再传，否则金额会被当成多余参数丢掉）：

```bash
adb shell "cmd notification post -S bigtext -t '测试' dshtest5 '支付 ¥12.34'"
```

App 侧日志：

```
I/NotificationCapture: 通知监听已连接
I/NotificationCapture: 已记账：其他 12.34 规则=fallback_expense     ← 记账
I/NotificationCapture: 重复丢弃：其他 12.34                          ← 去重
```

数据库实读：

```
transactions 行数: 1
  (id=1, amount=12.34, direction='EXPENSE', sourceName='其他',
   merchant=None, rawText='测试 支付 ¥12.34')
```

**解析 → 记账 → 跨来源去重 → 入库，四个环节在 Android 15 真机上全部正确。**

### 「认不出就留档」机制有效

真机上的微信通知被正确留档为 `matched=0`（即导出时的 `[UNMATCHED]`）：

```
[21:28:42] pkg=com.tencent.mm  text='42 [2条]42: [转账] 请收款'
[21:28:47] pkg=com.tencent.mm  text='test [转账] 已被接收'
```

这正是设计意图：**用户平时不会主动报告问题，App 自己把证据留下来。**
本次验收正是靠这份留档才定位到「通知里没有金额」这个事实。

## 五、真实样本（用于校准规则）

### 微信「转账给好友」的系统通知 —— **不含金额**

```
42 [2条]42: [转账] 请收款
test [转账] 已被接收
```

> **重要结论**：微信/支付宝的**转账**类通知只说「转账」，不带金额。
> 因此这类支付**无法**从通知里记账 —— 不是规则写得不好，是信息本身不存在。
> 正确做法是留档 + 不记账（宁可漏记，也不能瞎编金额），
> 漏掉的用「设置 → 导入账单」补。

### 银行/支付验证码短信

```
微信支付 【微信支付】027626(微信支付验证码,请勿泄露),
```

> 应当被排除，不记账也不留档。
