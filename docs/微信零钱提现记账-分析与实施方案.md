# 微信零钱提现记账 — 功能分析与实施方案

> **结论先说**（TL;DR）
>
> 1. **现在这个功能只做了一半，而且是做错的那一半。**
>    代码里已有 2 条微信提现规则，但它们把提现记成一条 **NEUTRAL（中性）** 的记录。
>    你的预期是「**零钱侧记支出 + 银行侧记收入，两笔**」，现在**一笔都不符合**。
> 2. **「微信侧记一笔支出」现在被有意堵死了**：规则明确标成 `NEUTRAL`，
>    `NEUTRAL` 不进支出统计也不进收入统计，所以你在统计里**看不到这笔钱**。
>    这正是你「发现没有记录」的直接原因。
> 3. **「银行侧记一笔收入」能不能成，取决于银行侧文案**，而这恰恰是最危险的地方：
>    现有短信规则里的「到账」二字会把「提现到账」记成 **INCOME**，
>    但「零钱提现」这个词本身在微信侧也会命中规则 —— 两边很可能**根本不是**你说的
>    「两笔钱完全一样」，详见 [§2.3](#23-关键发现你以为的两笔钱其实只有一笔是确定的)。
> 4. **技术上没有绕不过去的难点**，工作量约 **1~2 天**（含测试）。
>    真正的难点不是「怎么写正则」，而是 **4 个业务判断必须由你来定**，见 [§6](#六需要你拍板的四个问题)。
> 5. **⚠️ 不建议直接动手改。** 当前方案下「提现两笔」会和现有去重机制**打架**，
>    还会**污染收入统计**，详见 [§5](#五方案选型我只推荐-a)。

本文档基于**当前主干代码实读**（非推测）写成，所有结论都标了文件与行号，可逐条核对。

## 一、你的预期 vs 实际行为

| 环节 | 你的预期 | 代码实际行为 | 差在哪 |
|---|---|---|---|
| 微信零钱提现 | 记 **1 笔支出** 500 元 | 记 1 笔 **NEUTRAL** 500 元（若金额抓得到） | 方向被有意标成「中性」；中性不进任何统计 |
| 银行到账 | 记 **1 笔收入** 500 元 | 视文案而定，可能记、可能不记、可能记成中性 | 见 [§2.3](#23-关键发现你以为的两笔钱其实只有一笔是确定的) |
| 两笔金额一致 | 「完全一样」 | **指纹不同，谁也管不住谁** | 指纹含方向，一收一支是两个指纹 |

**一句话**：不是「没记录」，是「记成了你不想要的样子」+「部分场景金额都抓不到」。

用现有 5 条相关规则（`wechat_withdraw_settled` / `wechat_receive` / `wechat_withdraw` /
`wechat_pay_merchant` / `wechat_pay_generic`）按优先级模拟匹配：

|---|---|---|---|---|

| `微信零钱提现到账通知` | 无 | – | – | ⚠️ 完全不记 |
| `微信支付 零钱提现申请已提交` | 无 | – | – | ⚠️ 完全不记 |
| `【微信支付】零钱提现 500.00元 已到账,请查收` | `wechat_withdraw_settled` | **⚠️ 抓不到** | – | ❌ 命中了但金额组为空，引擎跳过 → 不记 |

**复现方式**（不用装 Android，Python 即可）：


> 第 3、4、5 行说明：现在的规则**只认「提现」二字后面紧跟金额**的写法。
> 只要你手机上的微信通知多几个字（比如「申请已提交」「已到账，请查收」），
> 就会**既不记账、也不报错** —— 静默漏记，用户完全无从察觉。
>
> ⚠️ 第 6 行还暴露一个**真实的空捕获 bug**：`([\d,]+\.?\d*)` 里的 `[\d,]+` 和 `\.?\d*`
> 都是可空的，所以这个组**能匹配空串**。一旦「到账」后面的数字不是它想要的形态
> （这里是「已到账,」逗号紧跟），它匹配到空字符串，`parseAmount("")` 返回 null，
> 引擎 `continue` 换下一条规则 → **整条通知静默丢弃**。
> 见 `ParseEngine.kt:122-123`。修规则时必须一并处理。

### 2.3 关键发现：你以为的「两笔钱」其实只有一笔是确定的

你说「银行零钱提现到账记录收入一笔钱，两笔钱完全一样」。这里有个**重要的认知偏差**：

**微信的零钱提现，银行侧收到的是一条「**转入/到账**」短信，而不是「提现」短信。**

对照 `BuiltinRules.kt:262-273` 里的 `sms_transfer_neutral` 规则：

```kotlin
pattern = Regex("""(?:提现|充值|转存|转账)\s*(?:金额)?\s*(?:人民币)?\s*[¥￥]?\s*([\d,]+\.?\d*)\s*元"""),
direction = Direction.NEUTRAL,
priority = 22,
```

它会把**任何含「提现」二字的银行短信**抓成 NEUTRAL。于是有两种走向：

| 银行短信实际文案 | 命中规则 | 结果 | 是否符合你预期 |
|---|---|---|---|
| `您尾号1234账户提现人民币500.00元` | `sms_transfer_neutral` (22) | **NEUTRAL** 500 | ❌ 你要 INCOME |
| `您尾号1234账户**提现到账**人民币500.00元` | `sms_transfer_neutral` (22) 先命中 | **NEUTRAL** 500 | ❌ 你要 INCOME |
| `您尾号1234账户**到账**人民币500.00元` | `sms_income` (30) | **INCOME** 500 | ✅ |
| `您尾号1234账户**转入**人民币500.00元` | `sms_income` (30) | **INCOME** 500 | ✅ |

**规律**：
- 银行短信里凡是**带「提现」二字**的 → 被 `sms_transfer_neutral`（优先级 22）抓成中性；
- 只有**不带「提现」**的（到账/转入/存入/入账）→ 才是 `sms_income`（优先级 30）记成收入。

**而且更要注意**：`sms_income` 的动词表里**有「到账」**。
如果哪家银行发的文案是「您的**零钱提现到账** 500.00 元」，
`sms_transfer_neutral` 会因为同时含「提现」而**抢先**（22 在 30 之后确实慢，
但 `sms_income` 要求「到账」后面直接跟金额 —— 这里是「到账 500.00 元」，
两个规则**都可能命中**，谁先取决于具体文案的字符间隔）。

> ✅ **这一条必须用你的真实短信来定**，不能靠猜。
> 拿到原文之前，任何方案都只是在赌。

### 2.4 去重机制会怎么处理这两笔

`app/src/main/java/com/moneyflow/app/parse/Fingerprint.kt:29-35`

```kotlin
fun of(amount: Double, direction: Direction): String {
    val raw = "%.2f|%s".format(amount, direction.name)   // ← 指纹 = 金额 + 方向
    ...
}
```

我实测验证过：

```
微信提现 EXPENSE : 303c18a9c9daff2cf7abe7dfa07ca6ca
银行到账 INCOME  : 5b549c9b0eab9d29487fc16e06ed77a2
两者相等吗？        False
```

**结论：指纹含方向，所以「一笔支出 + 一笔收入」天然是两个不同指纹，
去重机制不会把它们合并 —— 这点对你是好消息。**

但反过来看，**这也意味着去重保护不了你**：
如果微信侧和银行侧**同时被记成同方向的同一笔**（比如都成了收入），
指纹相同 + 时间在 ±90 秒内（`TransactionRepository.kt:152`）→ 只留一条。
这反而是**现在**唯一能防重复的机制。

## 三、为什么你「发现没有记录」

按可能性从高到低排列，**建议你按这个顺序去查**：

| # | 原因 | 怎么验证 |
|---|---|---|
| 1 | **记了，但记成了 NEUTRAL，统计上看不见** | 首页列表里应该有那条记录，金额是**黑色数字、没有 +/- 号**（`Fmt.kt:29`）。点开看方向 |
| 2 | **通知文案不在现有规则的覆盖范围内**，静默丢弃 | 设置 → 导出样本，找 `[UNMATCHED]` 里含「提现」的条目 |
| 3 | **金额组匹配到空串**（§2.2 第 6 行的 bug），命中规则却不记账 | 同上，看 `raw_samples` 表里 `matched=0` 的记录 |
| 4 | **微信通知里根本没有金额**（和「转账」情况一样） | 看通知原文，如果只有「零钱提现申请已提交」这类无金额文案 —— 那就是数据源限制，无解 |
| 5 | **监听掉线了**，压根没收到通知 | 设置页第 1 项是否显示「已授权·未连接」 |

> **请注意**：`ParseEngine` 对匹配不到金额的文本是**静默返回 `NoAmount`** 的
> （`ParseEngine.kt:149`），而 `NotificationCaptureService` 只在
> `MoneyText.looksMoneyRelated()` 为真时才留档（`NotificationCaptureService.kt:144`）。
> 「零钱提现」含「提现」二字，在 `MoneyText.MONEY_MARKERS` 里（`MoneyText.kt:40`），
> **所以它一定会被留档** —— 这是好消息，你的证据应该还在。

## 四、能不能实现？技术难点清单

**结论：能实现，且没有绕不过去的难点。** 下面是需要处理的技术点，按难度排序。

### 4.1 难度低 —— 纯规则改动

| 难点 | 说明 | 处理方式 |
|---|---|---|
| 方向要从 NEUTRAL 改成 EXPENSE | 一行改动 | 改 `direction` 字段 |
| 通知文案形态多样 | 「零钱提现 ¥500」「…手续费 0.10 元 到账 500.00 元」「提现 500.00 元已到账」 | 加规则 + 用真实样本校准 |
| 空捕获组 bug | §2.2 第 6 行：`([\d,]+\.?\d*)` 可匹配空串 | 收紧正则为 `(\d[\d,]*(?:\.\d{1,2})?)`，或在引擎里把空串视为「没匹配」 |
| 手续费被当成提现金额 | 已在 `wechat_withdraw_settled` 里处理过（README bug 记录） | 保持现有做法，加回归测试 |

### 4.2 难度中 —— 需要新增数据模型（约 0.5 天）

**这是本方案唯一需要动表结构的地方。**

要满足「两笔钱互相知道对方」，需要一个**关联字段**。当前 `TransactionEntity`
（`app/src/main/java/com/moneyflow/app/data/TransactionEntity.kt`）没有这个能力：

```kotlin
// 现有字段，无法表达「这两条是同一笔资金流动」
val fingerprint: String? = null,   // 只含金额+方向，不含关联关系
val category: String? = null,      // 预留未用
```

**推荐做法（改动最小）**：复用已有的 `category` 字段，不新增列、**不需要数据库迁移**。

```
category = "提现:txfd-<毫秒时间戳>"
```

同一笔提现的两条记录共享同一个 `category` 值，UI 和后续对账都能靠它配对。
> 设计意图本来就写着「加功能不需要改表结构」（`交接文档.md:246`），
> 这里正好用上。

**如果坚持要显式字段**，则需新增 `transferId: String?` + 数据库 **v3 → v4 迁移**：

`app/src/main/java/com/moneyflow/app/data/AppDatabase.kt:99-124` 里有现成的
`MIGRATION_2_3` 可以照抄，且 `app/src/androidTest/.../MigrationTest.kt` 有迁移测试框架。
**成本：+0.5 天。**

### 4.3 难度中高 —— 跨来源关联（真正的技术难点）

「微信侧记支出」和「银行侧记收入」是**两条独立到达的记录**：

- 来源不同（`SourceKind.WECHAT_NOTIFICATION` vs `BANK_SMS`）
- 到达时间不同（可能相差几秒到几分钟）
- 各自的规则独立触发，`ParseEngine` 是**无状态**的（`ParseEngine.kt:34`，只有 `parse()` 一个入口）

**所以「让它们互相知道」必须在 `TransactionRepository` 层做**，大致逻辑：

```
收到一条「提现」/「提现到账」记录时：
  1. 在 ±N 分钟窗口内查找「另一侧、金额相同、方向相反」的记录
  2. 找到 → 两条都打上同一个 transferId，标记为已配对
  3. 找不到 → 先入库，打上 transferId，标记为「待配对」
```

**风险点**（必须处理，否则会错配）：

| 风险 | 后果 | 缓解 |
|---|---|---|
| 窗口内恰好有另一笔同金额的钱 | **错配**，把无关的两笔绑在一起 | 窗口取小（建议 **≤10 分钟**），且要求两侧**方向相反**、**来源分别是微信和银行** |
| 银行短信延迟很久（跨天） | 配不上，永远「待配对」 | 允许用户手动配对；或提供「待配对」列表 |
| 同一天提现两次相同金额 | 交叉错配 | 用「就近配对」（时间最近的优先） |

> **我的建议**：**第一版不做自动配对。**
> 两条记录各自独立、正确入账即可满足你的核心诉求（零钱减 500、银行加 500）。
> 配对是「锦上添花」，把它放到第二版，等你用一段时间、确认真的需要再上。
> 这样本方案从 1~2 天降到 **0.5 天**。

### 4.4 难度中 —— 收入统计会被污染

这是**最容易被忽略、但后果最严重**的一点。

首页的「本月支出 / 收入」算法（`TransactionListScreen.kt:257-262`）：

```kotlin
val expense = monthItems.filter { it.direction == Direction.EXPENSE }.sumOf { it.amount }
val income  = monthItems.filter { it.direction == Direction.INCOME  }.sumOf { it.amount }
```

**没有任何过滤。** 于是：

- 每次提现 500 元 → 「本月收入」**虚增 500**
- 提现 10 次 → 收入虚增 5000，**你的收入数字彻底失去意义**

**这正是现有代码把提现标成 `NEUTRAL` 的原因**（`BuiltinRules.kt:244-245` 注释写得很清楚：

> 「方向标记为 NEUTRAL：因为还款/提现/充值往往是账户间转移，
> 当成支出或收入都会让统计失真。」）

**所以：要让「提现记支出 + 到账记收入」，就必须先解决统计口径问题。**
可选方案见 [§5](#五方案选型我只推荐-a)。

### 4.5 难度低但必须做 —— 回归测试

项目约定明确写着（`交接文档.md:298-302`）：

> **宁可漏记，不可记错**；**改动 `ParseEngine` / `BuiltinRules` /
> `TransactionRepository` / `MoneyText` 后必须跑测试。**

需要新增的回归用例（放 `app/src/test/java/com/moneyflow/app/`）：

| 用例 | 守住什么 |
|---|---|
| `wechatWithdrawIsExpenseNotNeutral` | 提现必须记成支出（推翻旧断言） |
| `withdrawDoesNotCaptureFeeOrOrderNumber` | **已存在**（`ParseEngineJUnitTest.kt:140`），改方向后仍必须通过 |
| `withdrawWithEmptyAmountGroupIsIgnored` | §2.2 的空捕获 bug |
| `bankSmsWithdrawArrivalIsIncome` | 银行侧到账必须记收入 |
| `withdrawPairIsNotDeduplicated` | 一收一支**不能**被去重吃掉（指纹不同） |

## 五、方案选型（我只推荐 A）

### 方案 A ✅ 推荐 —— 提现记支出（不计入统计）+ 到账记收入

| 侧 | 方向 | 是否进统计 |
|---|---|---|
| 微信零钱 | `EXPENSE` | ❌ 不计入「本月支出」 |
| 银行到账 | `INCOME` | ❌ 不计入「本月收入」 |

**为什么推荐**：这是**唯一**同时满足「你要看到两笔」和「统计不失真」的方案。
实现上只需给 `TransactionEntity` 加一个 `countsInStats: Boolean`（或复用 `category`
加个前缀判断），UI 汇总时过滤掉即可。

**代价**：汇总卡片上要加一行说明（「不含提现等账户间转移」），否则用户会疑惑
「为什么我提现了 500，支出没变」。

**工作量：约 1 天**（含测试与文档）。

---

### 方案 B —— 提现记支出并计入统计（不推荐）

**后果**：收入/支出**双向虚增**。提现 500 会同时让「本月支出 +500」和「本月收入 +500」，
月度结余不变（这点是对的），但**两个绝对数字都失真**。

只有一种情况下可以接受：**你把这个 App 当「银行流水全量镜像」用，
而不是当「消费记账」用**。如果你是这个用法，方案 B 反而更简单（改一行 `direction`）。

**工作量：约 0.5 天。**

### 方案 C —— 保持 NEUTRAL，但把它显示出来（最保守）

**不改方向**，只改 UI：让 NEUTRAL 记录在统计卡片上单独显示一行
「账户转移 ¥N（不计收支）」。

**优点**：零风险，不碰去重、不碰统计口径、不需要数据模型改动。
**缺点**：不满足你「一笔支出 + 一笔收入」的原始诉求。

**工作量：约 2 小时。**

## 六、需要你拍板的四个问题

**在动手之前，这 4 个问题必须先有答案。** 尤其是第 1、2 条，猜错会导致返工。

### 问题 1（最关键）：你的银行到账短信原文是什么？

请给我**一条真实的**（脱敏即可，金额可以改成 500.00）：

```
候选 A：您尾号1234账户提现人民币500.00元
候选 B：您尾号1234账户提现到账人民币500.00元
候选 C：您尾号1234账户到账人民币500.00元
候选 D：您尾号1234账户转入人民币500.00元
候选 E：（其他，请照抄原文）
```

**为什么必须问**：见 [§2.3](#23-关键发现你以为的两笔钱其实只有一笔是确定的) ——
A/B 会被 `sms_transfer_neutral` 抓成中性，C/D 才会被 `sms_income` 记成收入。
**这直接决定要不要改银行短信规则。**

> 📌 **怎么拿**：App 里 `设置 → 导出样本`，把含「提现」的那条原文复制给我。
> 或者直接看手机短信。

### 问题 2：你的微信提现通知原文是什么？

请给我**一条真实的**：

```
候选 A：微信支付 零钱提现 ¥500.00
候选 B：微信支付 零钱提现 手续费 0.10 元 到账 500.00 元
候选 C：微信支付 零钱提现申请已提交
候选 D：零钱提现 500.00 元已到账
候选 E：（其他）
```

**为什么必须问**：§2.2 已证明，现有规则**只覆盖 A、B 两种**，C、D 会静默丢弃。
如果你的原文是 C，说明**通知里根本没有金额** —— 那时只能走「待确认转账」那套
补金额流程，和「转账无金额」是同一类数据源限制，**不是代码能解决的**。

### 问题 3：统计口径 —— 提现算不算「支出」？

- **选 A（推荐）**：列表里显示为支出，但**不进**「本月支出」汇总 → 统计不失真
- **选 B**：显示为支出，也进「本月支出」汇总 → 支出和收入**双向虚增**
- **选 C**：保持中性，只在汇总里单列一行「账户转移」

### 问题 4：支付宝余额提现要不要一起做？

支付宝的「余额提现到银行卡」是**完全一样的场景**。
现有代码里**没有**支付宝提现规则 —— 也就是说**支付宝提现现在连中性记录都没有**。
建议一起做（增量成本很低，约 +2 小时）。
