## 一、这个项目是什么

Android **本地**自动记账 App。读取微信/支付宝/银行的通知与短信，自动识别金额与
收支方向，生成流水并跨来源去重。

| 项目 | 值 |
|---|---|
| 包名 | `com.moneyflow.app` |
| 版本 | `versionCode=1`，`versionName=0.1.0` |
| 最低版本 | Android 8.0 (API 26)，`targetSdk=34` |
| 技术栈 | Kotlin + Jetpack Compose + Room（KSP） |
| 网络 | **Manifest 里没有申请 INTERNET 权限**，这是隐私承诺的一部分，不要加 |
| 项目根目录 | `D:\Accounting tool` |

### 目录速查

```
app/src/main/java/com/moneyflow/app/
├── MainActivity.kt              页面路由（6 个页面，不用导航库，就是一个 enum 切换）
├── MoneyFlowApp.kt              Application，启动保活服务、声明运行时权限
├── data/                        数据层（Room）
│   ├── TransactionEntity.kt     流水实体
│   ├── TransactionDao.kt
│   ├── AppDatabase.kt           数据库 + 枚举转换器（当前 version=2）
│   ├── TransactionRepository.kt ★ 去重逻辑的唯一入口 insertDeduplicated()
│   ├── RawSampleEntity.kt       未知格式留档表
│   └── SampleRecorder.kt        留档写入
├── parse/                       解析引擎（项目核心）
│   ├── ParseRule.kt             规则数据结构
│   ├── BuiltinRules.kt          ★ 规则表：识别不准就改这里
│   ├── ParseEngine.kt           ★ 匹配、金额提取、指纹生成
│   ├── Fingerprint.kt           指纹算法（通知与 CSV 共用，必须唯一）
│   ├── MoneyText.kt             ★ 「看起来和钱有关」判定（含验证码排除）
│   ├── CustomRuleStore.kt       用户自定义规则持久化
│   └── MiniJson.kt              手写的极小 JSON 解析（不引第三方库）
├── capture/                     系统抓取层
│   ├── NotificationCaptureService.kt ★ 通知监听（主要数据源）
│   ├── SmsReceiver.kt                 短信接收
│   ├── KeepAliveService.kt            ★ 前台保活 + 监听看门狗
│   └── BootReceiver.kt                开机自启
├── csv/                         CSV 账单解析（支付宝/微信）
└── ui/                          Compose 界面（SettingsScreen 是权限与工具入口）
```

### 数据流

```
微信/支付宝/银行 App 通知 ┐
                          ├→ NotificationCaptureService ┐
银行短信 ─────────────────┘                              │
                                                          ├→ ParseEngine.parse()
银行短信 ──→ SmsReceiver ─────────────────────────────────┘        │
                                                                   ↓
                                                        命中规则？→ 金额+方向+商户
                                                                   ↓
                                                      生成指纹（只含 金额+方向）
                                                                   ↓
                                            Repository.insertDeduplicated()
                                                                   ↓
                                          ±90 秒内有同指纹？→ 丢弃
                                                        否 ↓
                                                    写入 Room → 首页自动刷新
```

⚠️ **指纹故意不含来源、不含分钟**。含分钟会导致「跨分钟边界的同一笔钱记两次」
（真机踩过，见 README bug 1）。时间维度由 Repository 的 ±90 秒范围查询负责。

### ⚠️ 本机 shell 的坑（每条都实际卡过我）

1. **`JAVA_HOME` 要用 Windows 路径**，`/c/...` 形式对 `.bat`（如 `apksigner.bat`）无效：
   ```bash
   export JAVA_HOME='C:\Users\24996\jdk17\jdk-17.0.20.1+1'   # 对 .bat
   export JAVA_HOME="/c/Users/24996/jdk17/jdk-17.0.20.1+1"   # 对 gradlew（bash 脚本）
   ```
2. **调 adb 时加 `export MSYS_NO_PATHCONV=1`**，否则 `/sdcard/xxx` 会被 MSYS 改写成
   Windows 路径，报 `cannot create file/directory`。
3. **`adb shell` 会把命令再解析一次**。要传带空格的文本，必须整体再套一层引号：
   ```bash
   adb shell "cmd notification post -S bigtext -t '标题' tag '支付 ¥12.34'"
   # 少了外层引号，¥12.34 会被当成多余参数丢掉（我为此白查了半小时）
   ```
4. **写文件用 `ops_*` 工具，不要用 `cat`**。中文文件一律 UTF-8。

## 四、⚠️ 待解决的问题（按优先级）

### P0 — 影响核心可用性

#### 1. 监听服务掉线后在部分 ROM 上无法自动恢复

**现象**：`通知使用权` 显示已开启，但系统没有绑定监听服务，App 收不到任何通知，
用户付款后毫无记录、毫无提示。真机（REDMI K80 / HyperOS）实测复现。

**现状**：
- 已加看门狗（`KeepAliveService`，60 秒周期检查「已授权但未连接」并 `requestRebind`）
- 真机验证：看门狗**能检测**掉线并持续重试，**能检测**恢复后停止重试
- ❌ **但 HyperOS 忽略 App 发起的重连请求**，重试 3 次都没成功
- 真正有效的是用户手动「把系统开关关掉再打开」

**想解决的方向**（都没验证过，自己判断）：
- 调研是否有其它合法手段触发系统重绑（`requestRebind` 之外的 API）
- 至少让用户**更快发现**：目前只有打开设置页才看得到状态，
  可考虑在检测到掉线时发一条提醒通知（注意别变成骚扰）
- 引导用户开「自启动」（小米），这是社区公认的缓解手段，但**未在本机验证过有效性**

**关键文件**：`capture/KeepAliveService.kt`、`capture/NotificationCaptureService.kt`、
`ui/SettingsScreen.kt`（状态显示与手动步骤文案）

#### 2. 微信/支付宝规则缺真实样本（P3 未完）

**现状**：`BuiltinRules.kt` 里微信/支付宝的规则是**按「常见格式」猜写的**，
从未用该用户的真实通知校准过。银行短信规则是校准过的（19/19）。

**真机已确认的坏消息**：**微信/支付宝的「转账」通知里没有金额**，
原文就是 `test [转账] 已被接收`。这类支付从通知通道**无法**记账，
正确行为是留档 + 不记账（现已如此），漏掉的靠账单导入补。

**缺的样本**（拿到就能改规则）：

| 想要的 | 用来验证哪条规则 |
|---|---|
| 微信**商家扫码付款**成功通知 | `wechat_pay_merchant` / `wechat_pay_generic` |
| 支付宝**付款成功**通知 | `alipay_pay` / `alipay_pay_merchant` |
| 任意一家银行**消费/入账短信**（该用户手机的） | `sms_expense` / `sms_income` 系列 |
| 银行 App 自身的交易通知 | 目前只走 `fallback_expense` 兜底 |

**怎么拿**：让用户在 App 里 `设置 → 导出样本`，把 `[UNMATCHED]` 的原文发出来。
或者直接读数据库（见下方「调试技巧」）。

## 五、必须遵守的项目约定

### 1. 规则是数据，不是代码

识别不准**只改 `BuiltinRules.kt` 这张表**，不要动 `ParseEngine` 的匹配逻辑。

```kotlin
ParseRule(
    id = "wechat_pay_merchant",
    sourceKind = SourceKind.WECHAT_NOTIFICATION,
    sourceName = "微信支付",
    packageNames = setOf("com.tencent.mm"),
    pattern = Regex("""向\s*(.{1,20}?)\s*(?:付款|支付)\s*[¥￥]?\s*([\d,]+\.?\d*)"""),
    amountGroup = 2,
    direction = Direction.EXPENSE,
    merchantGroup = 1,
)
```

改完**必须**跑 `python tools/real_sms_check.py` 和 `tools/rule_check.py`。

### 2. ⚠️ `smsOnly` 不能乱用也不能乱删

银行短信规则故意写得很宽松（金额后可能没有「元」字、动词有十几种）。
如果让它们去匹配 App 通知，会**因优先级更高而抢走微信/支付宝的匹配**，
导致商户名丢失、来源标错 —— 这个 bug 真实发生过。

所以宽松规则一律标 `smsOnly = true`。
回归测试：`wechatMerchantRuleNotStolenByBroadSmsRule`。

### 3. ⚠️ 验证码绝不能留档

README 和设置页都向用户承诺过。判定逻辑**只有一份**：`parse/MoneyText.kt`。
不要再在别的文件里复制一份 markers 列表 ——
`NotificationCaptureService` 和 `SmsReceiver` 曾经各有一份，
结果就是「通知不记验证码、短信却记」。回归测试在 `MoneyTextTest`。

### 4. ⚠️ 指纹算法只有一个实现

`parse/Fingerprint.kt`，通知通道和 CSV 导入共用。
两边不一致 → 跨来源去重失效。不要再复制。

### 5. 宁可漏记，不可记错

没有金额就不记账（`ParseResult.NoAmount`），不要「猜」一个金额。
验证码、聊天记录不记。所有「看起来和钱有关但没识别出来」的留档，
让用户能导出。

### 6. 文档要说真话

这个项目的 README 里明确区分「✅ 已实测」「⏸ 未验证」。
**不要把「模拟器跑通」写成「已验证」**，也不要保留被实测推翻的说法
（比如已经删掉的「打开 App 即可自愈」）。

## 六、真机调试技巧（省时间）

### 连手机

```bash
export MSYS_NO_PATHCONV=1
ADB=/c/Android/Sdk/platform-tools/adb.exe
"$ADB" devices -l
```

当前测试机：**REDMI K80（`24117RK2CC`）/ Android 15 / HyperOS V816 / arm64-v8a**，
带**应用分身 XSpace（user 999）**。

### 看监听到底有没有真的绑上 ⚠️ 最关键的一条

**「已授权」不代表「已连接」**，必须分开查：

```bash
# 静态授权（设置里那个开关）
adb shell settings get secure enabled_notification_listeners

# 动态状态（服务是否真被系统绑上）—— 这个才是真相
adb shell dumpsys notification | sed -n '/Live notification listeners/,/Snoozed/p' | grep -i moneyflow
# 输出为空 = 掉线了，App 收不到任何通知
```

### 强制恢复监听

```bash
C="com.moneyflow.app/com.moneyflow.app.capture.NotificationCaptureService"
adb shell cmd notification disallow_listener "$C"; sleep 2
adb shell cmd notification allow_listener    "$C"
```

⚠️ 这也**会改变** `enabled_notification_listeners`，所以没法用它伪造
「已授权但未连接」这个状态去测看门狗 —— 要复现那个状态，
用 `adb install -r` 覆盖安装（实测能稳定触发）。

### 伪造一条通知，验证全链路（不用花钱）

```bash
adb logcat -c
adb shell "cmd notification post -S bigtext -t '测试' tag1 '支付 ¥12.34'"
sleep 4
adb logcat -d -s NotificationCapture:V
# 期望：I/NotificationCapture: 已记账：其他 12.34 规则=fallback_expense
# 再发一条同金额 → 期望：重复丢弃：其他 12.34
```

⚠️ 命令里那层**外层引号不能省**，否则金额会被 shell 拆掉，通知里只剩「支付」两个字。

### 读数据库（release 包读不了）

release 包 `debuggable=false`，`run-as` 会拒绝。两个办法：

**办法 A**：临时装 debug 包（与 release **同一签名**，数据不丢）

```bash

adb exec-out run-as com.moneyflow.app cat databases/moneyflow.db-shm > /tmp/m.db-shm
```

查 `transactions` 和 `raw_samples` 两张表。

⚠️ 装 debug 包会杀进程 → 监听掉线 → 用上面的 `cmd notification` 重新绑。

**办法 B**（推荐给用户）：让用户 `设置 → 导出样本`，他直接看到 `[UNMATCHED]` 原文。

### 让 logcat 只显示 App 的日志

App 的日志 TAG：`NotificationCapture`、`SmsReceiver`、`KeepAliveService`、`BootReceiver`。
关键的几行：

```

解析失败：<原因>                           ← Failure 分支
通知监听已连接 / 已断开                    ← 绑定状态变化
已授权但监听未连接，第 N 次请求重连        ← 看门狗在工作
通知监听已恢复（之前掉线 N 次）            ← 看门狗确认恢复
```

注意：**解析结果为 `NoAmount` 时是静默的**（正常通知大多没金额，打日志会刷屏）。
所以「日志里什么都没有」**不代表**没收到通知 —— 要看 `raw_samples` 表才知道。

## 七、下一步建议（我的判断，你可以重新评估）

按「对用户价值 ÷ 成本」排序：

1. **让用户补一次真实样本**（最低成本，最高收益）
   要一条**商家扫码付款**的微信/支付宝通知原文 + 一条银行卡消费短信。
   拿到就能把 P3 从「银行短信 19/19」推进到「微信/支付宝也校准过」。
   → 用 `设置 → 导出样本`，或者用上面的 debug 包读库。

2. **真机跑一次仪器测试**（成本很低）
   `bash tools/run_all_tests.sh --device`，把 26 个用例从模拟器 Android 14
   迁到真机 Android 15 上验证，顺便确认迁移测试在 Android 15 上没问题。

3. **隔夜保活验证**（成本低，但要等一晚）
   睡前不划掉 App，第二天看夜里的支付有没有漏记。
   这决定问题 4 是否成立，也决定要不要上 `AlarmManager` / `WorkManager` 兜底。

4. **P0 问题 1 的进一步调研**（成本中，收益中）
   看能否找到比 `requestRebind` 更可靠的重绑手段；
   或者接受现实，改为「让用户更快发现掉线」（掉线时发一条本地提醒）。

5. **P5 分类 / 报表 / 预算**（成本高）
   只有在用户明确要的时候再做。数据库已预留字段，不需要迁移。

**不建议现在做的**：加云同步、加网络请求（违背「纯本地」的核心卖点）。

## 九、这次验收留下的教训（写给下一个人，也写给未来的我）

1. **「授权开着」≠「功能可用」。** 整整 40 分钟都花在这个错觉上。
   查系统状态要查**动态的那一层**（live listener），不是静态配置。
2. **日志里没有 ≠ 什么都没发生。** App 对非账务通知是静默的，
   必须读数据库或看留档样本才有真相。
3. **先怀疑自己的测试方法，再怀疑代码。** 伪造通知时因为少了一层引号，
   我一度以为解析引擎坏了 —— 实际上发出去的通知里只有「支付」两个字。
4. **模拟器测不出 ROM 行为。** 应用分身、监听被解绑、`requestRebind` 无效，
   这三条在模拟器上**一个都复现不了**。
5. **文档里被推翻的说法要及时删。** 「打开 App 即可自愈」曾经写在 README、
   安装文档、验收清单三处，实测无效。留着它比不写更糟。
